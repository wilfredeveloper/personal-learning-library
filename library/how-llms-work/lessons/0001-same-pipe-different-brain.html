Everything "intelligent" about this chatbot is getSimpleChatResponse, a chain of checks in the spirit of Weizenbaum's ELIZA (1966):

Why ELIZA still mattersIt used only this kind of string surgery, yet people confided in it. Weizenbaum wrote the paper partly to show how little was going on inside.

Notice the return type: one string, the whole reply. The function is done before any streaming starts.

The pipe: four hops from function to pixels

1. Route. The handler splits the reply on spaces and emits a start event, one word event per word, then done (simple-chat.ts:100–106).

2. Emit. emit(data, event, delay) writes one event with JSON.stringify(data), then sleeps for delay ms. The pacing is deliberate: 1000 ms after start, 200 ms after each word. So the 2.2 s is \(1000 + 6 \times 200 = 2200\) ms. Nothing was being "thought" during those sleeps.

3. Wire. One HTTP response that stays open. The browser spec says each data: line adds to the event's data, and a blank line dispatches the event. If the stream ends before that blank line, the half-event is thrown away (WHATWG HTML, §9.2).

4. Read. readSSE pulls raw chunks off response.body. A chunk can end mid-line, so it splits on \n and puts the unfinished last piece back: buffer = lines.pop() (client/lib/sse.ts:90–91). Each complete data: line is JSON-parsed and handed to the hook, which appends the word and re-renders the bubble.

Same plumbing, different routesEvery section of the repo streams this way: BPE merge steps, training epochs, generated samples. You'll see this pipe in every lesson.

ELIZA

The reply is a deterministic function of the message: \(\text{reply} = f(\text{message})\).

The whole reply exists before byte one. Streaming is presentation: the future words are already queued.

A language model

The reply is sampled one token at a time, each from a probability distribution.

Token 3 does not exist until token 2 has been chosen and fed back in. Streaming is the computation itself leaking out.

The equation at the end of the pipe

A language model is a function that takes the tokens so far and returns a probability for every token in its vocabulary being next:

\[ p_\theta(x_t \mid x_{<t}) \]

Read it as "the probability of token \(x_t\) at position \(t\), given (the bar \(\mid\)) all the tokens before it, \(x_{<t} = x_1, \dots, x_{t-1}\)." The subscript \(\theta\) (theta) names the model's parameters, the numbers training adjusts. For the toy model those are just the table entries. For the repo's transformer they're every weight matrix it trains (lesson 7 counts them with countParams).

Why is "next token, given the past" enough to score a whole reply? Because of the chain rule of probability. It follows from the definition of conditional probability, \(P(A, B) = P(A)\,P(B \mid A)\), applied over and over. For three tokens:

\[ P(x_1, x_2, x_3) = P(x_1)\; P(x_2 \mid x_1)\; P(x_3 \mid x_1, x_2), \]

and for any length \(T\), with \(\prod\) meaning "multiply together for \(t = 1\) up to \(T\)":

\[ P(x_1, \dots, x_T) = \prod_{t=1}^{T} p_\theta(x_t \mid x_{<t}). \]

That's the P(reply) line in the simulator: one factor per token, each the bar height of the token that was picked. No approximation is involved. Any distribution over sequences can be written this way. The modelling choice is how \(p_\theta\) computes each factor: one token back for the toy, the whole context via attention for a transformer.

Generation runs the equation forwards. Sample (draw at random, weighted by probability) a token from the distribution, append it, and ask again:

\[ x_t \sim p_\theta(\,\cdot \mid x_{<t}), \qquad t = 1, 2, \dots \text{ until an end token.} \]

The \(\sim\) means "is drawn from", and the dot \(\cdot\) stands for "any token". This loop is literally generateText in src/routes/train-transformer/transformer.ts:832–905. It runs a forward pass on the context, takes the last position's scores, turns them into probabilities, samples one token, pushes it onto ids, and repeats. Temperature and top-p, the two knobs in that function, get their own lesson (9).

One practical wrinkle. Multiply 200 probabilities of 0.5 and you get \(0.5^{200} \approx 6 \times 10^{-61}\), smaller than the smallest number a 32-bit float can hold (about \(10^{-45}\)). It rounds to zero. So we work in logs, which turn the product into a sum:

\[ \log P(x_1, \dots, x_T) = \sum_{t=1}^{T} \log p_\theta(x_t \mid x_{<t}). \]

Each \(\log p\) is negative (since \(p \le 1\)), so the sum just grows more negative instead of vanishing. The negative of this average is the cross-entropy loss the repo's transformer trains on. You'll meet it as crossEntropyLoss in lesson 8.

The one idea to keep

The streaming pipe (route → emit → event-stream → readSSE → hook) is identical for ELIZA and for GPT. What differs is the brain. ELIZA computes the whole reply, then drips it out. An LLM computes \(p_\theta(x_t \mid x_{<t})\), samples one token, feeds it back, and repeats, so each streamed token is a fresh step of the computation. The chain rule makes those per-token probabilities multiply into the probability of the whole reply.

Check yourself

1. In the repo's Simple Chat, when does the full reply first exist?

Line 97 computes the full string; the loop at 103–105 only paces it out. That's the "presentation, not computation" half of the contrast.

2. In the event-stream format, what makes the browser dispatch an event?

Per the WHATWG spec, the blank line dispatches. An event cut off before its blank line is discarded.

3. Why does readSSE do buffer = lines.pop()?

A chunk can end mid-line. The last split piece may be incomplete, so it waits in the buffer until the next chunk finishes it.

4. In an LLM, why can't token 3 be computed before token 2?

\(x_3 \sim p_\theta(\cdot \mid x_1, x_2)\): the distribution for token 3 takes token 2 as input, so token 2 must be chosen first.

5. A two-token reply: the model gave its first token probability 0.5, then the second 0.4. What is \(P(\text{reply})\)?

\(0.5 \times 0.4 = 0.2\). In logs: \(\log 0.5 + \log 0.4 \approx -0.69 - 0.92 = -1.61\), and \(e^{-1.61} \approx 0.2\).

6. Why do models add log-probabilities instead of multiplying probabilities?

Hundreds of factors below 1 multiply to something smaller than a float can hold. A sum of logs stays a manageable negative number.
